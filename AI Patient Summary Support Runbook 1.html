AI Patient Summary - Support Runbook

Operational guide for support teams: feature enablement, configuration, trigger behavior, manual execution patterns, and verification steps.

Enablement Trigger Flow Manual/API Call Troubleshooting

1) What the feature does

  • Generates two patient-level HTML reports after exam finalization:
  • Detailed report: PatientHistoryDetails.html
  • Summary report: PatientHistorySummary.html
  • Stores reports under patient repository path: {Repository.Root}\{PatientId}\
  • Sample path: C:\Medstreaming\demomode\dbRepository\PatientHistory\1\PatientHistoryDetails.html
  • Reports are accessed in UI from Previous Exams tab using AI History Details and AI History Summary tabs.

2) When job starts

  • Primary trigger: exam finalization flow in business layer.
  • If no patient history file exists, baseline job is created.
  • If history file exists, incremental job is created.
  • Job XML is written to configured spool directory and picked by standalone parser timer loop.
Web service decides whether to enqueue based on FeaturePatientHistoryAiSummaryEnabled. Standalone parser reads full AI settings at startup.

3) Required configuration

All parser settings are under PatientHistoryAiSummarySettings in Server.xml.

Server.xml sample

<PatientHistoryAiSummarySettings>
  <FeaturePatientHistoryAiSummaryEnabled>true</FeaturePatientHistoryAiSummaryEnabled>
  <BaselineMissionId>39535</BaselineMissionId>
  <IncrementalMissionId>39538</IncrementalMissionId>
  <BaselineFolderId>30992</BaselineFolderId>
  <IncrementalFolderId>30993</IncrementalFolderId>
  <EnableRetrieveForHistory>false</EnableRetrieveForHistory>
  <ReArchiveAfterHistory>true</ReArchiveAfterHistory>
  <ImportCycleInterval>5</ImportCycleInterval>
  <StartupOptions></StartupOptions>
</PatientHistoryAiSummarySettings>

FeaturePatientHistoryAiSummaryEnabledboolMaster feature switch for enqueue from finalization flowtrue/false
BaselineMissionIdstringMission used for first patient-level generationExample: 39535
IncrementalMissionIdstringMission used for updates after baseline existsExample: 39538

API key is read from environment variable MATCHA_API_KEY by standalone parser at startup, not from web.config.

4) Call path (receive -> route -> process)

  1. Receive: User finalizes report in UI.
  2. Route: Finalization handler checks patient history file existence and routes as baseline or incremental.
  3. Enqueue: JobManager.AddJob(job, PatientHistoryAiSummaryJobStorageDir) writes job XML.
  4. Pickup: SAPatientHistoryAiSummaryQueue polls spool directory at ImportCycleInterval.
  5. Process: PatientHistoryAiSummaryProcessor anonymizes PDF, calls AI mission, re-injects PHI, writes HTML.
  6. Publish: UI tabs read generated files in Previous Exams area.
This feature is handled by a separate standalone parser EXE, so it does not change the normal JobParser pipeline or the HL7Outbound parser flow.

5) How to call it manually

Option A - Normal application flow (recommended)

  1. Set FeaturePatientHistoryAiSummaryEnabled=true.
  2. Finalize an exam for a patient.
  3. Verify job XML appears in patient history spool directory.
  4. Wait for parser cycle, then verify two HTML files are created in patient folder.

Option B - API baseline trigger (if endpoint is enabled in your build)

Endpoint documented in implementation plan:

POST /api/PatientHistorySummary/RequestBaseline/{patientId}

Example:

curl -X POST "http://localhost/MedStreaming.WebService/api/PatientHistorySummary/RequestBaseline/12345"

Option C - Batch generation pattern using SQLCMD (support operation)

Similar to your ForwardingUtility pattern, generate a daily batch that calls baseline endpoint per patient. Update URL, auth headers, and SQL filter for your environment. 

@echo off
set MEDSTREAMING_SQL=YOUR_SQL_SERVER
set MEDSTREAMING_API_BASE=http://localhost/MedStreaming.WebService

for /f "tokens=1-4 delims=/- " %%A in ('date /t') do set today=%%A%%B%%C

"C:\Program Files (x86)\Microsoft SQL Server\Client SDK\ODBC\130\Tools\Binn\SQLCMD" -S %MEDSTREAMING_SQL% -d Medstreaming -Q "SET NOCOUNT ON;
SELECT TOP 1000
'curl -X POST ""'+ '%MEDSTREAMING_API_BASE%' + '/api/PatientHistorySummary/RequestBaseline/' + CONVERT(varchar, Exam.PatientId, 10) + '""'
FROM Exam
WHERE DATEDIFF(DD, Exam.DateTime, GETDATE()) > 180
  AND (Exam.IsDeleted IS NULL OR Exam.IsDeleted <> 1)
GROUP BY Exam.PatientId
ORDER BY MIN(Exam.DateTime) ASC" -h -1 > C:\Medstreaming\config\AI_PatientSummary\RunBaseline_%today%.bat

call C:\Medstreaming\config\AI_PatientSummary\RunBaseline_%today%.bat
Use patient-level triggering for baseline to avoid unnecessary duplicate exam-level calls.

6) Standalone parser EXE and folders

The feature runs in its own executable: MedStreaming.PatientHistoryAiSummary.exe. It owns its own queue path and processing folders so it stays isolated from other parsers.

PathPurpose
PatientHistoryAiSummaryJobStorageDirQueue folder where job XML is written and picked by the standalone parser
...\error\Move failed job XML or failed work items for support review
...\processed\Move successfully processed job XML after completion
The queue, error, and processed folders are only for the new PatientHistoryAiSummary parser. They do not affect the JobParser or HL7Outbound parser paths.

7) Verification checklist

  • Feature flag is enabled.
  • Mission and folder IDs are valid for baseline and incremental.
  • Spool directory exists and job XML files are created.
  • Standalone parser process is running and polling.
  • Output files exist in patient folder.
  • UI Previous Exams shows AI History Details and AI History Summary tabs.

8) Fast troubleshooting

Receive stage

  • No job queued after finalize: check feature flag and finalization success path.
  • Wrong job type: verify history file existence logic baseline vs incremental.

Route stage

  • Job XML not in spool: check write permissions and configured storage directory.
  • Duplicate baseline jobs: validate concurrent finalize behavior and patient sequencing.

Process stage

  • Parser not processing: verify parser service/process startup and poll interval.
  • AI call fails: verify MATCHA_API_KEY, mission IDs, folder IDs, outbound connectivity.
  • Archived exam skip: review EnableRetrieveForHistory and retrieval flow status.
If processing fails repeatedly, preserve spool XML and logs before manual cleanup for RCA.
